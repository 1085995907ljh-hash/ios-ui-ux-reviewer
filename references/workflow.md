# 执行流程

## 1. 确定项目和范围

先读项目 AGENTS.md。用 `rg --files` 定位 `.xcodeproj/project.pbxproj`、`.xcworkspace/contents.xcworkspacedata`、Package.swift、Swift、Storyboard、XIB、Info.plist、xcstrings、Assets.xcassets 和 StoreKit 配置。排除构建产物、Pods 和第三方依赖，除非问题涉及它们。

查看 Git 状态；非 Git 项目也可以审查。记录分支与提交或文件快照信息。不要读取无关个人目录。不要输出配置中的密钥。

输入可以是项目路径、当前工程、指定页面、代码加截图。没有 Xcode 项目时，仍可审查提供的源码或截图，但说明范围。截图单独不能确定源码位置。

默认检查主流程、共享控件和高风险入口。大项目先列出页面清单与本轮优先级，不能把抽查写成全量审查。已有明确范围时不要重复提问。

## 2. 读交互链，不只读 View

SwiftUI：入口 App、NavigationStack、TabView、sheet、fullScreenCover、路由、环境对象、ViewModel、异步任务和持久化。

UIKit：App/SceneDelegate、导航控制器、标签控制器、ViewController、约束、Storyboard/XIB、delegate 和数据源。

对每个主要任务记录：起点 → 操作 → 等待 → 成功/失败 → 返回/取消。找出数据何时提交，何时清空，退出后如何恢复。

检查共享 Button、字体、颜色、间距封装、主题、字符串资源和权限配置。修饰符可能在父级，颜色可能由环境覆盖，点击范围可能被容器扩大。必须追踪这些来源。

## 3. 收集候选问题

按 audit-matrix.md 选择适用项。搜索固定高度、lineLimit、disabled、onTapGesture、dismiss、try?、catch、Task、授权请求等，只用于定位。

每个候选先问：具体影响哪类用户？在哪个条件发生？其他代码是否已经处理？是缺陷、建议，还是尚未证实的风险？

确认“缺少入口”前，检查设置、菜单、路由和共享组件。确认可达性前，检查真实 app target、条件编译、feature flag；仅在 Preview 或测试中的代码不能当成正式页面缺陷。

规则证据分为 Apple 审核要求、Apple 设计建议、项目约定、实践建议。当前官方原文优先于教学摘要。涉及支付、登录、权限、系统版本时，核对适用地区、版本和例外。不能联网时标明“官方要求未实时复核”，不要断言必定被拒审。

## 4. 验证实际界面

不要求用户打开 Xcode 窗口；工程目录足以开始。模拟器可用时优先用 XcodeBuildMCP。首次 build/run/test 前读取 session defaults，再按需要发现项目、设置 scheme 与 simulator。使用现有配置；不擅自改签名、依赖或后端。

操作前检查构建脚本和运行环境，避免自动触发部署、生产请求或外发。检查 UI 自动化能力是否可用。若只能截图，不能声称已测试点击流程。

测试正常主流程，以及实际可安全到达的失败、空状态、拒绝权限、取消和返回。使用支持的小屏、大字、深色、键盘、减弱动态效果场景。记录每个场景结果；不必机械排列全部组合。

保留设备型号、iOS 版本、语言、字号、外观、复现步骤、截图和必要的 UI 层级。真实 VoiceOver 焦点与朗读行为需要实际验证；只有层级信息时，写“语义信息检查”，不要写“VoiceOver 已通过”。

截图尺寸不是点击区域尺寸。代码色值不是透明合成后的对比度。只有有效测量时才给具体数值；否则列出测量步骤。

修改模拟器外观等可逆测试设置后恢复原值。不要擦除用户模拟器或删除已有数据。需要隔离时使用专用测试环境。购买、发消息、删除账户等只走明确授权的测试路径；否则停在确认前并记录未测。

构建失败、工具缺失、登录阻挡或后端不可用：保存错误摘要，继续能完成的源码审查。不要为了启动审查而修复业务代码。报告阻塞步骤及恢复条件。

## 5. 报告与复核

同一共享组件造成多处问题时合并为一个根因，列受影响页面。保留不同根因的问题。

交付前再次读取涉及文件的行号，核对截图与场景一致。建议落到具体组件、状态或布局，不写“优化体验”。不强行凑数量，不用主观总分伪装测量。

默认写报告，不改 App。用户后续要求修改时，按确认范围实施，再用原复现场景回归；原本只有源码证据的条目仍不能冒充运行验证。
