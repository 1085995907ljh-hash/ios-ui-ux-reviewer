# 审查报告格式

中文短句。一条结论只表达一个问题。先讲用户影响，再讲原因。英文 UI 的建议文案保留英文。

## 必须区分的证据状态

- **运行已复现**：有真实操作、环境和结果证据。
- **源码确认**：源码和调用链足以证明具体逻辑问题；尚未运行。
- **待验证风险**：条件、可达性或视觉表现未确认。单独列出，不算已发现缺陷。
- **可选改进**：没有明确功能或可用性缺陷，仅为有理由的设计建议。

不把模型信心百分比当成证据。没有发现问题时写“在已检查范围内未发现可确认问题”，并列未覆盖项。

## 严重程度

本技能统一使用此表，即使辅助 QA 技能的分级不同，也按用户影响重新归级。

| 级别 | 标准 |
|---|---|
| P0 | 已证实的大范围不可用、重大不可恢复数据损失或严重交易/隐私伤害，需立即处理；极少使用 |
| P1 | 核心任务无法完成、关键用户群无法操作，或明确高风险误操作 |
| P2 | 可用但明显困难、易误解或需绕路的交互/布局问题 |
| P3 | 局部一致性、措辞或视觉细节，影响较小 |

严重程度由实际影响和适用范围决定；不能看到“支付”或“无障碍”就自动定 P0。

## review.md 模板

```markdown
# <App> UI/UX 审查

日期：<date>。范围：<screens/flows>。
方式：<源码 / 源码与模拟器 / 截图>。
环境：<工程、target/scheme、提交或快照、设备、iOS、语言、字号、外观；未知写未知>。

## 主要问题

### F-01 [P1] <具体后果>

- 证据状态：源码确认 / 运行已复现。
- 场景与影响：<谁在什么条件下受影响>。
- 实际与预期：<可观察的差异>。
- 位置：[File.swift](<真实绝对路径>:<核实的行号>)，<函数/控件>。
- 证据：<相关调用链或短代码片段；运行证据附截图/层级/日志路径>。
- 步骤：<实际复现步骤；未运行则标“建议验证步骤”>。
- 依据：<审核要求/设计建议/项目约定/实践建议>，<官方链接与核对日期，如适用>。
- 修改建议：<修改哪个状态、组件或布局；默认最小改法>。
- 验收：<相同场景下能观察到的成功条件与必要回归>。

## 待验证与可选改进

<分开列出。风险附验证方法，不冒充确定缺陷。>

## 覆盖与限制

| 页面/流程 | 源码 | 运行场景 | 状态 | 未验证原因 |
|---|---|---|---|---|
| <screen> | <files> | <device/state> | 已检查/待验证/阻塞/不适用 | <reason> |

## 修改顺序

<按影响与依赖排序，引用 F 编号；不要虚构工时。>
```

没有源码时，位置用截图和控件名称，明确无法定位代码。不要编造文件路径或行号。

报告路径：`docs/ui-ux-reviews/<date>-<scope>/review.md`。同日同范围已有报告时加序号。证据放同目录。尊重项目指定目录；无写入权限或用户要求不落盘时，在回复中给完整报告。截图含个人信息时先避免捕获或做本地脱敏，不能上传到公共服务。
